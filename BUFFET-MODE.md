# Buffet mode — runbook (one file)

> **Status:** v2. User-approved 2026-11-11. Built on branch `buffet-v2`. This version replaces v1 (council-approved via P20–P24; decisions D1–D8 stand unless this runbook says otherwise — definitions: `skills/frontend-kit/references/decisions.md`).
> **What buffet mode is:** the humans hand over a brief, leave the machines, and go eat. The agents run the frontend loop autonomously (code + design together, no human in the loop). The humans come back and edit/finish directly on the Figma the agents made — or directly on the built product.
> **Terminology (corrected from v1):** each agent has its own **clone + branch**; **worktrees are the coordinator's trial tool**. The v1 wording (one worktree per agent) is wrong across machines and must not be used: a worktree is extra checkouts of one repository on one machine. Across four machines, the isolation unit is the clone + branch; the coordinator uses detached throwaway worktrees only to trial-merge and gate.

### What the chief coordinator decides (never delegates)

| Decides | Why |
|---|---|

The contract must be *more* complete up front than in a spawned-subagent system, because there is no mid-flight steering across machines. No board row is claimable until all six fields are filled. |
| Ownership table (slice → agent → file globs → round), filled BEFORE dispatch | Ownership-before-dispatch (P20). A claim whose globs overlap an owned glob is refused deterministically — the globs make the check mechanical, not judgemental. |

| Merge order + trial merges + landing (§5) | Single-writer rule (Cognition 2026, VERIFIED — see the Guardrails paragraph in §4). Only the coordinator merges, into the run's mainline. |
| Escalation to humans (`input-required`, run-invalid) | Only the coordinator escalates; workers never message humans directly about the run (standing instruction in each agent's task file at run start; detection is by human report; consequence: the coordinator marks the slice `input-required` and reassigns it when it learns of it — socially enforced, not technically enforced). |
| Human-facing milestone posts (Optimus group, one line, milestones only) | The coordinator is the only agent that posts there. Mie never posts there. |

### How the coordinator assigns work (publish → claim → award, no orders)

1. The coordinator publishes slices on `coord/BOARD.md` (one row per slice — schema in §3) with the 6-field TASK_TEMPLATE filled and the ownership table filled first.
2. An agent claims by writing in its OWN `coord/<name>.md` file: `CLAIM <slice-id> | plan: <2–3 lines> | files: <glob(s)> | board-hash: <hash> | at: <UTC>` — **claim-with-a-plan**. The file globs publish intent so others route around it. A claim without file globs is incomplete; the coordinator treats the slice as still unclaimed. `board-hash` is the `buffet/main` commit hash the agent read the board at: after fetching the board (`git fetch origin buffet/main`), `git rev-parse origin/buffet/main`. See §5 for the coordinator's stale-hash rejection.
3. **A claim is a request until the coordinator awards it.** The coordinator's next merge pass records the award: the board row becomes `working` with the agent's name, and the award is written in the run log. Work done before the award is at the agent's risk. Expected latency from claim to award is at most one merge pass (30 min) plus one of the agent's pulls (15 min). The agent learns it won by reading the board on its next pull.
4. **WIP = 1 per agent:** one active claim per agent. A transient second claim is allowed only in the same commit as posting DONE on the current slice.
5. A worker may refuse a slice: `DECLINED <slice-id> | reason: <one line>` in its own file → the coordinator moves the row to `declined` (new state, borrowed from A2A's `REJECTED`) and either re-specs or reassigns it. A declined slice is terminal for that agent, not for the slice: the coordinator may re-list it as `submitted` for another agent. (Contrast: an objection to an *in-flight* slice still goes in the worker's own file and the worker keeps working on the last agreed slice — it does not stall the run.)

### Who summons the neutral merger and the judge

The coordinator spawns the neutral merger and the judge as **its own subagents, on its own machine, in its own clone** (§5). The coordinator commands only its own subagent instances — that is the line. Mie, Migga, and Milo are separate agents on separate machines owned by other humans and are never commanded; they are coordinated only through the board. Fallback if the coordinator cannot spawn subagents on its machine: the coordinator publishes a `NEED-MERGER <pair>` row on the board and any agent may claim it as a slice (WIP=1 still applies), provided it is not the owner of either branch in the pair — the merger must be a fresh-context agent with no production history of either branch. Known limitation (design-carried, not a build error): with three workers each holding a slice, no eligible claimant may exist — then the coordinator uses its own fresh subagent, or the landing waits for human-on-return.

### Deputy + succession

- **Staleness test (what "the coordinator is dead" means):** the coordinator is stale only if **both** hold: (a) there is pending work — a claim, a completion, or a slice awaiting merge — that has been unprocessed for >20 min, **and** (b) no coordinator commit in that window. An idle coordinator with an empty queue is idle, not stale: no pending work means no takeover, whatever the clock says. The coordinator may make a lightweight liveness commit to its own file (its last-seen line only) when it has no other work — a carve-out from the "never a commit of its own" rule, which binds workers, not the coordinator's proof of life.
- **Progress-signal heartbeat (D78):** while a run is live, the coordinator pushes one heartbeat line every 15 min in its own `coord/<name>.md` (Last-seen section): `HB <UTC> stage=<stage> next=<next action> progress=<short hash of the newest commit/PR this run produced, or "none"> blocked=<short reason with underscores, or "none"> pending=<count of unprocessed pending items>`. A NEW progress hash, or a blocked reason that appeared, changed, or cleared, is progress. Two consecutive no-progress cycles — three consecutive heartbeat lines, pairwise identical, `blocked=none`, spanning ≥30 min — escalate to the Deputy. A blocked reason that is reported and stable is legitimate: the 60-min clock applies instead (same reason unchanged ≥60 min from first appearance → the Deputy intervenes: reassign the unblock, escalate to humans, or mark the slice `input-required`). One no-progress cycle only is a warning, not an escalation. Enforcement is the deterministic 5-min cron probe (`coord/activation-probe.sh`): it reads the heartbeat lines and the pending-work marker at the remote tip and reports STALE / NO-PROGRESS / ERROR — it never takes over itself. **Clock ladder (D78, judgement call to be validated):** 20 min is the staleness clock. If the first rehearsal shows false-positive takeovers, the clock moves to 30 min before falling back to 60 min — never improvise a new number mid-run.
- **Two-phase takeover (fencing):** (1) the deputy posts `COORDINATOR TAKEOVER <UTC time> — reason: <pending work unprocessed since X> — last coordinator commit <hash> — term: <N+1>` in its own file and pushes; (2) the deputy **waits one full pull cycle (15 min) before acting as coordinator**. If the old coordinator posts `COORDINATOR ALIVE <UTC>` in its own file and pushes inside that window, the takeover is void and the deputy stands down (posts `TAKEOVER VOID — coordinator alive`). (3) After the window with no alive-signal, the deputy owns the board: it writes `coordinator-term: <N+1>` in the board (the board carries a `coordinator-term: N` field, starting at 1 for Muse at run start; each takeover increments it). **Every coordinator board write carries its term; agents and the old coordinator ignore board writes from a superseded term.** The old coordinator, on seeing a higher term, posts `STOOD-DOWN` in its own file and resumes as a worker. This term number is the fencing token — it is what makes "exactly one coordinator" a property of the protocol instead of an assertion.
- **The deputy's own work on takeover:** the deputy's active claim is **suspended** — marked `input-required` with the note "deputy became coordinator; claim suspended", and reassigned by the new coordinator to another agent or re-listed. This resolves the WIP=1 collision (the deputy cannot simultaneously coordinate and hold a slice) and the builder-never-grades collision: **slices the deputy built but has not landed are frozen** — they stay `working` under the deputy's name but the deputy-coordinator does not land or stop-decide them; they are carried to the human-return packet. A deputy who built a slice never merges it.
- **Fallback if the deputy is also stale:** the backup deputy takes over by the same procedure (same staleness test, same two-phase takeover, same term increment). If both deputies are stale, the run **pauses**: all slices go to `input-required` with the blocker named, and the run waits for human-on-return. There is no third deputy and no silent continuation without a coordinator.
- **In-flight merge at takeover (RUNBOOK PROCEDURE — the design is silent here):** a merge the old coordinator landed locally but has not pushed is NOT a land — the new coordinator treats any slice with no land record on the remote mainline as unlanded and re-trials it from the remote mainline tip before landing it. The old coordinator, on posting `STOOD-DOWN`, must not push any local merge afterwards; if it already pushed before seeing the higher term, the new coordinator reverts it (`git revert -m 1`, F23) and re-trials. A duplicate land is detected by the run log: a slice whose land is already recorded on the remote is never re-landed.

## 2. The coordination channel (binding)

**The real coordination channel is the REPO (git).** Task board + handoff logs + run log live as files in this repo: `coord/BOARD.md` (coordinator-owned), one file per agent (`coord/muse.md`, `coord/mie.md`, `coord/migga.md`, `coord/milo.md`), per-slice task files (`coord/tasks/<slice-id>.md`), and coordinator-only append-only `coord/run-log.jsonl`. GitHub is public, so every agent can clone/pull from any machine. Push requires the §9 grant (shared-repo branches primary; fork + PR fallback) — before the grant, an agent can clone/pull but cannot push. This is the only channel all four agents can read/write without a human relay and without spamming anyone. *MCP is how an agent reaches a tool; git is how agents reach each other.*

**The Optimus Messenger group is for HUMAN-FACING MILESTONES ONLY.** Short status lines a human can glance at from the buffet — e.g. "xong phần X, đang làm Y". No agent-to-agent coordination chatter in the group, ever: it floods the team chat, each message goes out as the human owner, and agents only see the group when pinged or during checks (no push, high latency, no addressing). Never use the group to assign work, debate a decision, report an error, or ask another agent a question — that goes in `coord/`.

**Mie cannot speak in the Optimus group at all — Mie's human owner is not an Optimus member. Do NOT propose adding Mie's human owner to the team group just for this.** Mie coordinates through `coord/mie.md` + the repo only. If a milestone needs to reach the humans, the coordinator (Muse) posts it.

**The coordinator cannot command the other three agents directly.** There is no order channel. Coordination works because all four follow this runbook: the coordinator writes assignments into `coord/BOARD.md`, each agent reads its own handoff file, does the slice, logs it, and the coordinator merges. If an agent disagrees with an assignment, it writes the objection in its own handoff file and keeps working on the last agreed slice — it does not stall the run waiting for an answer.

## 3. Where the work lives

- **This repo (the kit):** the skill, the loop, the runbook, `coord/`. Clone-and-go: `git clone https://github.com/phamTuan207/frontend-agent-kit.git`, follow the README paste-prompt, run `./install.sh` then `./verify.sh`.
- **Each agent's work:** its own **clone** on its own machine, its own branch `buffet/<name>`. One agent = one branch = one clone. Nobody edits another agent's files. Nobody edits `coord/BOARD.md` except the coordinator. Each agent edits ONLY its own `coord/<name>.md` (append-mostly).
- **The run's mainline:** `buffet/main`. The coordinator creates it at run start from `main` if it does not exist (setup commands below) and records `Mainline: buffet/main` in a board field. Only the coordinator merges into it.
- **The run log:** `coord/run-log.jsonl` — **coordinator-only**. Agents log by writing events in their own `coord/<name>.md` files; the coordinator transcribes into `coord/run-log.jsonl` on each merge pass. Single writer, no merge conflict, at the cost of up to 30 min of log latency. (v1's "each agent appends to the shared log" was corrected: two agents appending one line each from different branches conflict on the log when the coordinator lands the second branch — both appends sit at the same end-of-file position relative to the common base — and v1 had no log-merge rule.) The run log is append-only: never edit a line; supersede by appending. **Run-log entry schema (minimal, binding — this is what F14/F21 "re-append the loser's rows from the run log" reads back):** one JSON object per line with `ts` (UTC ISO-8601, the coordinator's observation time), `actor` (agent name), `term` (coordinator-term at the time), `event` (e.g. `claim`, `award`, `land`, `lapse`, `takeover`, `board`), `slice` (slice id or `—`), and `board-row` (snapshot of the affected board row: slice / owner / status / expected-min / files / notes), and `board-fields` (snapshot of the board-level fields at the time: `Deputy`, `coordinator-term`, `Flagged files` — so a two-term board conflict over board-level fields can be re-appended from the log, F14/F21, not just slice rows). The three pre-existing entries (2026-11-10) predate this schema and carry no `ts`/`board-row` fields — they are legacy, not a pattern to copy.
- **The project being built:** `design/` (TASTE.md, tokens.css, demo.html, references/, screenshots/, variants/), `design/figma-ground-truth/` (frame PNG + context JSON + SOURCE.md), `design/figma-export/` (SOURCE.md + SKIPPED.md if the export was skipped), `design/run-log.jsonl` (the per-project run log — not the same file as `coord/run-log.jsonl`).
- **The Figma file:** one file per project, Pages 01 Cover / 02 Design System / 03 Screens (structure in §6). The Figma file URL + node IDs live in `design/figma-ground-truth/SOURCE.md` and `design/figma-export/SOURCE.md`.
- **Coordinator's trial checkouts:** **detached throwaway worktrees**, created and removed per trial: `git worktree add --detach /tmp/trial-<a>-<b> <trial-commit>`; `git worktree remove /tmp/trial-<a>-<b>` after the land decision for that slice (gate + cross-check + grade — the cross-check runs on the merged tree in the trial worktree, so the worktree must survive through it). Never describe the agents' clones as worktrees. The worktree is the coordinator's inspection/gating tool, not the agents' isolation mechanism.
- **Single-machine subagents (if ever):** one worktree per agent on its own branch, sharing one `.git`. On ONE machine, one worktree per agent IS the right pattern (and Claude Code documents it as `isolation: worktree`). Enable `extensions.worktreeConfig` if this becomes real (config is shared across worktrees by default).

### Board row schema

Each board row carries `Slice | Owner | Status | Expected-min | Files | Notes`. `Notes` links to `coord/tasks/<slice-id>.md` — one coordinator-written file per slice, holding the six TASK_TEMPLATE fields (objective / output format / tools-sources / boundaries / effort scale / definition of done). `Expected-min` is the numeric effort estimate in minutes for the lease (§5); the coordinator writes it at dispatch. The ownership table carries `File-glob | Agent | Round`.

### Board fields

The board carries, as fields at the top: `Mainline: buffet/main`, `Deputy: <name> (backup: <name>)`, and `coordinator-term: N` (starting at 1 for Muse at run start; each takeover increments it).

### Run trigger

The coordinator writes a **"Run trigger" section at the top of `coord/BOARD.md` at run start, before the humans leave**, recording verbatim: the brief, the Figma link (or "none"), the target (landing / dashboard / redesign), and the return time. If the brief lives only in a human's message, the coordinator copies it verbatim into the trigger section at run start. The brief-compliance checks (F2/F9) judge against this section and the slice task files — never against a human's message that no agent can re-read.

### Run-start sequence: inventory + census FIRST, then the workflow decision

The order is binding: no slice is published before the coordinator has read the inventory and the census.

- **`INVENTORY REQUEST` (design §6: the coordinator posts `INVENTORY REQUEST` + `CENSUS REQUEST` on the board before any slice is published).** The coordinator posts `INVENTORY REQUEST <UTC>` on the board (same board location as the census request, §4). Each agent replies in its own file within one pull cycle (15 min) with a `TOOLS` block: every CLI it can actually run, with version output — verified by running the command, never assumed — plus whether it can run sub-agents and how. Format: `TOOLS <UTC> — <cli> <version-output> — subagents: <yes/no/how> — notes: <...>`. The census reply rides with it: live sub-agent count, per-sub-agent task + status, stalled/dead ones with last activity (format in §4). The coordinator reads both replies on its first merge pass, aggregates them into the run log, and only then publishes slices. The coordinator self-reports its own tools + sub-agent count the same way (see `coord/muse.md`).
- **Tool inventory:** each agent posts a `TOOLS` block in its own file at run start, verified by running the command (e.g. `<cli> --version`), never assumed. Format: `TOOLS <UTC> — <cli> <version-output> — subagents: <yes/no/how> — notes: <...>`. CLIs known to be on the team's machines (verified 2026-11-11): Claude Code, OpenCode, Codex, and **agy — Google's Antigravity CLI** (the terminal successor to Gemini CLI, which Google shut down for free/Pro/Ultra users on 2026-06-18; a Go binary; multi-agent by default; `-p` runs a prompt non-interactively; skills, hooks, subagents, and MCP support — verified via convergent secondaries). Its vendor install is `curl | bash` — the inventory records only whether it is already installed; the kit never runs a `curl | sh` install (kit-forbidden). **The coordinator only assigns work a machine can actually do:** a slice needing a Claude Code worktree goes only to a machine with Claude Code; a slice needing Codex hooks goes only to a Codex machine (and Codex hooks need per-human trust before they fire). An agent whose machine lacks a needed tool reports the exact failure instead of improvising.
- **Census:** the §4 protocol (board request → own-file reports → coordinator aggregates → one-line milestone to the Optimus group). At run start the census runs with the inventory; the coordinator self-reports its own tools + sub-agent count the same way.
- **The decision they feed:** after the first merge pass reads the inventory + census, the coordinator publishes slices sized to what exists (fleet depth → slice size; missing tools → slice reassigned or re-specced). An agent that never reports (no inventory, no census) is treated as absent for this run — no slice is published for it until it reports.

## 4. The run sequence

**Trigger:** a human starts a buffet run with a brief + (optionally) a Figma file link, then LEAVES. The trigger names: the brief, the Figma link (or "none"), the target (landing / dashboard / redesign), and the return time. No human input is expected again until the return. Starting a run without a human present to answer OAuth is valid ONLY if Figma paths A/B are pre-seeded (exported JSON/PNGs already in the project) or MCP is already authenticated in that session; otherwise the run starts in Figma-degraded mode — it does NOT wait for a human. The trigger step includes a **link check while a human is still present** (F24): a dead Figma link is recorded as Figma-degraded before departure, not discovered mid-run.

**Run-start order (binding):** inventory + census FIRST (§3), then the workflow decision. No slice is published before the coordinator has read both.

0. **Setup:** create `design/` from `skills/frontend-kit/templates/design/` + `design/figma-ground-truth/` + `design/figma-export/`. Figma input in order: (A) native-export DTCG JSON → converter → `tokens.css` draft; (B) PAT one-shot import → PNGs into `design/references/` + token draft; (C) MCP read — ONLY on catalog hosts AND only after the user's Figma for Education status is confirmed. **A8 hard rule:** no Figma-derived value enters `tokens.css` or a grade unless its source output is saved under `design/figma-ground-truth/` with URL + version + access date. A value with no saved source file is fabricated; the round is invalid. On ANY Figma auth/quota failure: stop the Figma path, log the exact human step, continue WITHOUT Figma.
1. **Taste lock:** builder + experts advise; coordinator records the lock (`skills/frontend-kit/scripts/run-log.mjs lock`). `tokens.css` + references committed BEFORE any HTML.
2. **Build:** one HTML file, tokens only. Vague brief → 5 structural variants + 1 break-frame = 6 variants; human-less pick uses the deterministic auto-pick (`skills/frontend-kit/scripts/variant-picker.mjs pick --auto`). Figma frames may INSPIRE a variant; a variant is never imported from a frame. **D2 (weakened variant contract):** variants use the same content/copy/section inventory; structure may differ.
3. **Gate:** `impeccable detect` + gate scripts + html-validate/pa11y. FAIL blocks the round. NO Figma in the gate (no comparison tool exists); advisory Figma-baseline pixel-diff may be printed, never FAIL-blocking.
4. **Cross-check (§14):** the dedicated cross-check team runs on the merged tree in the trial worktree — after the deterministic gate, before the judge grade. SEVERE blocks the land exactly as a gate FAIL does. **D7:** P3 is split — annotation INTEGRATE; self-check only in the reworked 1-pass post-gate visual-P0-only report-only form.
5. **Eyes + grade:** Playwright screenshots 1440/768/390; independent judge grades with evidence lines. If a Figma file exists: Figma-as-ground-truth — "Figma \<value\> vs built \<value\>" per score, from the CACHED ground-truth files (re-pull only on Figma version change). Mobile scores without a Figma frame say so explicitly. **D8 judge-input whitelist:** the judge sees screenshots + locked reference shots + rubric/scope + lock text + tool measurements + pairwise A/B inputs. Forbidden: model/builder identity, earlier scores, run log, gate findings. Only a single `gate: green` bit and a single `cross-check: clear` bit reach the judge, enforced by the orchestrator. The 80% Layout/Space agreement threshold applies only at n≥32 scores, report-only below; a systematic overshoot ≥1.0pt on any axis triggers a rubric-anchor rewrite.
6. **Fix top 2 as token diffs** (`tokens.css` first). Fixes NEVER go to Figma mid-loop.
7. **Stop:** stop at ≥4 on every axis AND gate green AND cross-check clear, or after 3 rounds per direction (max 2 re-picks, 9 rounds total). Best version kept across re-picks. The run ends in "awaiting human" state — the human-gate packet is NOT prepared yet (it is prepared once, at step 8, after the pre-ship cross-check).
8. **Pre-ship cross-check (once, on the shipping version, §14)** — then prepare the human-gate packet (score table + 3-width screenshots + questions + recommended next command), once.
9. **Figma handoff export (once, after the loop stops):** export the shipped state to Figma (§6). If write-back is unavailable, write `design/figma-export/SKIPPED.md` (tool attempted, exact error, seat/host) and end the run successfully with the HTML/CSS artifacts.
10. **Return:** humans come back — see §7.
11. **Dream step (§13):** after the human-return packet, before the next run.

**Stop conditions:** (a) ≥4 all axes + gate green + cross-check clear; (b) 3 rounds in a direction → re-pick (max 2); (c) 9th round ends regardless — present the best version; (d) Figma failure → degrade, do not stop the run; (e) QC/red-team SEVERE finding (fabrication, invented Figma data, builder self-grade) → run invalid, redo from the last valid lock, never patch over it.

**Census protocol (a designed step, not an afterthought):** `INVENTORY REQUEST` (§3) is posted together with `CENSUS REQUEST`; both replies arrive in the agents' own files within one pull cycle. The chief coordinator must know, on the day, how many sub-agents each of Milo, Mie, and Migga has alive underneath — because the fleet depth decides slice sizing and stall detection. The census runs through repo/git shared state only (the coordinator cannot command the other three; there is no order channel):
- **How the check happens:** the coordinator publishes `CENSUS REQUEST <UTC>` on the board. Each agent reports in its own `coord/<name>.md` file and pushes. The coordinator reads the reports on its next merge pass and aggregates them into the run log. The Optimus Messenger group carries only a one-line human-facing summary per census round (e.g. "Census 13:00: 4 agents alive, 9 sub-agents, 1 stalled (Migga's reviewer, last active 12:40)") — the census itself is coordination state and lives in the repo, not in the group.
- **What each agent reports (format):** `CENSUS <UTC> — live: <n> — <sub-1>: <task> (<working|stalled|dead>, last active <UTC>) — ... — stalled/dead: <names>`. Stalled = no progress for >30 min. Dead = the agent cannot reach it, or it exited without reporting. The count is live sub-agents only (finished ones are not counted; the run log holds the history).
- **Cadence on the day:** at run start (with the inventory), at the mid-run checkpoint (~50%), and on demand — the coordinator posts a new CENSUS REQUEST whenever it needs a fresh count (after a stall, before a big slice, after a takeover).
- **What the census decides:** slice sizing (an agent with live sub-agents can take a bigger slice — its fleet parallelises *inside* the slice; an agent with 0 live sub-agents gets a smaller slice); stall detection (an agent reporting stalled/dead sub-agents gets its slice checked — reassigned or split by the coordinator). The census is a report, not an order channel: the coordinator never commands a sub-agent, and sub-agents work inside their owning agent's slice only. WIP=1 is per top-level agent and is unchanged by the census — the fleet depth is the agent's own business; the coordinator only sizes the work to fit it.

**One mid-run integration checkpoint at ~50% (time set by the coordinator at run start; ~13:00–14:00 for a 09:00 start — the fraction governs if the run starts late):** the checkpoint **adds to a merge pass, it does not replace one** — the coordinator does the checkpoint sweep inside one scheduled 30-min merge pass, in the §5 landing order. Its output decides: the coordinator logs per-branch trial results + the gate result on the merged tree, and smoke-tests the demo path. A checkpoint conflict or gate-red tree **starts the neutral-merger path early (same as §5 early detection) but authorises NO landing** — only a trial against the current tip authorises a land. No duration is claimed for the checkpoint (it runs inside one merge pass). One checkpoint only; a second one is stand-up ritual, not integration. The mid-day **census round happens with the checkpoint**.

**Parallelise the portfolio, not the loop (P23, council-approved 2026-11-10 — INTEGRATE, unanimous, clean).** Four agents are faster than one only if the parallel work is independent. The loop's steps are coupled — one agent's output is the next step's input — so they stay sequential; the portfolio around the loop is where parallelism pays.

| SEQUENTIAL — one agent, in order, per page | PARALLEL — across agents, at the same time |
|---|---|
| Taste lock → build → deterministic gate → cross-check → grade → fix (the §4 steps, in order). No step starts until the previous step's artifact exists. | Different pages (each page runs its own sequential loop). |
| A fix round waits for its grade; a grade waits for its gate and cross-check. | The 5 CSS variants (same content/copy/HTML, only CSS changes — §4 step 2). |
| The stop decision waits for the grade + gate + cross-check of the current round. | Independent research angles (each angle is its own slice on the board). |
| | Expert-pack reviews — each expert judges ONLY its own domain, from the artifacts, in parallel (§1). |

The independent grader stays a separate role and **never grades its own branch** — a grader is a fresh sub-agent (or a different agent instance) with no production history of the build it grades (§1, §10). Parallelism never overrides that rule: if the only available grader built the branch, the grade is "gate green, vision not available" and the human gate carries the taste judgement.

**Guardrails (direction, not a buffet-mode forecast):** Kim et al. report **+80.8%** on decomposable tasks and **−70.0%** on sequential tasks when adding agents (v3 abstract — pin v3: v1 said +80.9% with 180 configs and 4 benchmarks; v3 has 260 configs and 6 benchmarks. The primary, arXiv:2512.08296, is CHƯA ĐỌC beyond the abstract + §1 — these figures are Kim et al.'s benchmarks, read via secondaries, not measurements of this loop and not a forecast for buffet mode). The loop above is the sequential case, so getting this table wrong makes buffet mode *slower* than solo. And the verified 2026 Cognition sentence (not a paraphrase): **"multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions."** The sentence "don't add agents to a step that already works" does NOT appear in Cognition's 2025 post — do not attribute it to Cognition; the idea belongs with Kim's capability-saturation finding (single-agent performance already above ~45% accuracy sees negative returns from collaboration).

## 5. Handoff protocol (how four agents work without talking)

**One file per agent, coordinator merges.** Each agent edits ONLY its own `coord/<name>.md` file. NOBODY edits another agent's file. NOBODY edits `coord/BOARD.md` except the coordinator. `coord/run-log.jsonl` is coordinator-only (§3) — agents log in their own files and the coordinator transcribes. `coord/run-log.jsonl` is append-only: NEVER edit a line already written — a stale or wrong record is superseded by appending a new record that says what it supersedes (P22). This is what makes concurrent work safe: there is no file two agents both write. Git is the transport in v2 — the repo is the coordination channel; there is no A2A/MCP layer (P22). A2A v1.0.0 is the latest released version (v1.0.1 exists on the releases page, 2026-05-28, bug fixes only — immaterial to the rejection); MCP 2026-07-28 is agent-to-tool, not agent-to-agent. Keep only the state vocabulary (including `declined`, borrowed from A2A's `REJECTED`).

**Claiming work (claim-with-a-plan):** the coordinator lists open slices on `coord/BOARD.md`. An agent claims a slice by writing `CLAIM <slice-id> | plan: <2–3 lines> | files: <glob(s)> | board-hash: <hash> | at: <UTC>` in its OWN file — never by editing the board. A claim without file globs is incomplete; the coordinator treats the slice as still unclaimed. `board-hash` is the `buffet/main` commit hash the agent read the board at (`git rev-parse origin/buffet/main` after fetching the board — see the merge-pass procedure below). A claim is a request until the coordinator awards it (§1).

**The claim arbiter:** "first push wins" is FALSE and is deleted from this runbook. Two agents push to *different* refs (`buffet/mie` vs `buffet/milo`); both pushes succeed — there is no shared ref to race on, so no push can lose. (B4mad's push-as-arbiter works only because their agents push status updates to the *same* ref; that mechanism does not transfer here.) The arbiter is the **coordinator's first-seen order**: the coordinator observes claims on its merge passes, in the order its pulls see them; the first claim observed wins, and the coordinator's merge records the award (the board row becomes `working` with the agent's name). The race window is up to one merge pass (30 min): two claims pushed before the same pass are first observed together. **Tie-break (deterministic, no clock trust):** in the fork case, the earlier PR creation time (a server timestamp — trustworthy, unlike agent clocks); otherwise the lexicographically smaller claim-commit hash. The loser's rule: the loser re-pulls and picks another slice; any work it did before the award is at its own risk — it never becomes a claim on the slice. The agent's own `at: <UTC>` timestamp in the claim is a note, never the arbiter: clocks are unsynchronised, and the coordinator's observation time is the only time that matters. **Stale board-hash rejection (design §12):** on the award pass the coordinator compares the claim's `board-hash` with the board version it is awarding from. The claim is rejected as stale if the cited board commit is no longer the current `buffet/main` tip AND the slice's row (status / owner / expected-min / files) changed since that commit — the agent re-claims against the current board. If the row is unchanged since the cited commit, the award stands and the coordinator logs the cited hash. To decide whether the row changed, compare the board at the cited commit with the current board: `git show <cited-hash>:coord/BOARD.md` (or `git diff <cited-hash> origin/buffet/main -- coord/BOARD.md`) and check the slice's row. A claim with no `board-hash` at all is incomplete, like a claim with no file globs.

**Delegation contract (P20, binding).** Every slice is dispatched with a filled `coord/TASK_TEMPLATE.md` — six mandatory fields: (1) objective, (2) output format, (3) tools/sources, (4) boundaries, (5) effort scale, (6) definition of done. **No board row is claimable until all six fields are filled** — an agent that finds an unfilled row writes `BLOCKED — template incomplete` in its own file and does not start. **Ownership before dispatch:** the coordinator fills the ownership table on `coord/BOARD.md` (file → agent → round) BEFORE dispatching, and **deterministically rejects claims on owned files** — a claim on a file another agent already owns for that round is refused, no judgement call, no negotiation; the claimant picks another slice. Why this exists: the largest measured failure category in multi-agent work is "system design issues" — **44.2% of labelled failures across 1,642 traces (MAST v3, Fig 1 / §4 body text: per-mode shares 11.8 + 1.5 + 15.7 + 2.8 + 12.4 = 44.2%; FC2 = 32.35%, FC3 = 23.5%)**. That is a share of *labelled failures*, NOT a per-run failure rate (per-system failure rates were 41%–86.7%). Source for the counts: the research synthesis (`research/coordination/SYNTHESIS.md` — workspace research note, not shipped in this repo, MAST row — 1,642 traces, 41%–86.7% per-system rates, FC2/FC3 shares, RT1-verified from MAST v3 §4 body text). The primary, arXiv:2503.13657, is CHƯA ĐỌC in full — the v3 shares are verified from v3 §4 body text via the research synthesis, not from a full primary read here. Version pins: v3 calls the category "(i) system design issues"; v2 called it "(i) specification issues"; v1's wording was "(i) specification and system design failures". The 41.77% figure is MAST **v2's** own published category share (200+ traces), quoted by DOMinic — not a DOMinic summation. Cite v3 only. Retired wordings, never use: the "~42–44%" range (conflates paper versions) and "specification"/"FC1" as the category name.

**Ownership does not prevent conflicts.** 47.3% of textual conflicts occur despite disjoint authored file sets (Xu et al. follow-up, arXiv:2610.04779, VERIFIED). Ownership reduces collisions; it cannot be the load-bearing control. Trial-merge + gate-on-merged-tree is.

**Board states (P22, binding).** Every board row carries one explicit state — `submitted → working → completed / failed / canceled`, plus `input-required` for a slice that is blocked and needs input (the coordinator resolves it or escalates it to the human; the Notes column names whose input is awaited), plus **`declined`** (§1). No new verbs beyond this sprint-minimum set. **Negotiation cap (D1 governs):** a slice that bounces between `input-required` and `working` **once without progress** is escalated to the human — a bounce without progress *is* a non-improving round, and D1 says escalate after the first one. "Progress" is judged by the coordinator from the record since the last bounce: new commits, a new plan in the claim, or gate movement. If none of those exist, the bounce is without progress. Mid-run with humans absent, the slice is marked `failed` with the blocker named and carried over to the human-return packet.

**Polling cadence (binding):** during an active buffet run, every agent runs `git pull --ff-only` **every 15 minutes** and reads `coord/BOARD.md` + its own handoff file — and, on the same poll, fetches the mainline explicitly (`git fetch origin buffet/main`, then read the board at `origin/buffet/main`), because a pull on the agent's own branch never sees the board (merge-pass procedure below). The coordinator merges + updates the board **every 30 minutes** (or immediately after a slice completes, whichever comes first) and publishes the board + run log after EVERY merge pass through the merge-pass procedure below (F18 — not only after lands — so the remote is at most one pass stale). Between polls, agents work from their local copy and write only to their own file. A merge conflict on your own file: routine pulls are `--ff-only`; rebase only your own unpushed commits — verify first with `git log --oneline origin/buffet/<name>..HEAD` (those are the unpushed commits; if the list is empty there is nothing to rebase); **never rebase commits already on origin** (the next push would need a force-push, which is forbidden); **never rebase another agent's branch** (D4). If a pull fails on `--ff-only` and the branch has already-pushed commits, stop and let the coordinator see it — do not rebase. Your file is append-mostly by construction, so conflicts should be rare; if one happens, keep both entries, never delete the other side's lines, and note it in your file for the coordinator to transcribe.

- **Adaptive backoff when idle:** empty queue → double the pull interval per empty cycle, max 2 h, reset to 15 min the moment a slice appears. **The deputy is exempt from backoff** — it polls every 15 min always (§1).
- **Immediate re-poll after completion:** after pushing a completed slice, the agent re-pulls immediately instead of waiting for the next 15-min tick.
- **Lease replaces the fixed stale rule:** a claim lapses after **60 min without a push** or **2× the slice's `expected-min`**, whichever is shorter. `Expected-min` is a numeric field on the board row, written by the coordinator at dispatch: defaults **S = 60, M = 240, L = 480** minutes; the coordinator may set a smaller number for a short slice. Note: with the defaults the 60-min cap binds for all three sizes (min(60, 120) = min(60, 480) = min(60, 960) = 60); the 2× term binds only when the coordinator sets `expected-min` below 30. **Renewal is by push only** — any push by the agent (a branch commit or an own-file update) resets both clocks. **The merge pass is the decision point:** a push after the lapse but before the pass revives the claim, so the effective lapse-to-reassignment latency is 60–90 min, stated not implied. On lapse the coordinator marks the slice `failed` (reassignable) and logs the lapse. "Stale with recent commits = slow, leave alone" stays. **Lease vs `input-required` (RUNBOOK PROCEDURE — the design is silent):** the lease clock PAUSES while a slice is `input-required` (tooling failure F26/F32, gate-red, or awaiting human input) and resumes when the slice returns to `working` on re-claim — a tooling outage must not mass-fail slices through the lease.
- **Liveness = pushes, full stop:** the coordinator's **only observation channel is pushes** — a last-seen line that is never pushed is invisible to the coordinator and renews nothing. On each merge pass the coordinator checks, in order: (1) commits/PR pushes on the agent's branch since the last pass, (2) own-file updates pushed since the last pass (carrying the last-seen line: `Last seen: <UTC> — task: <slice-id or —> — last commit: <short hash or —>`, one line in the Last seen section of the agent's own `coord/<name>.md`, updated on its normal 15-min pull, same commit as its other work). For research / no-commit slices this is the renewal path: the agent pushes its own-file update (last-seen line + progress note) and that push renews the lease — the last-seen line is a note carried by a push, not an independent signal. There is NO separate heartbeat schedule and NO extra commits for heartbeats (D5 stands; workers — the coordinator's liveness-commit carve-out is in §1). The 10/15/30/60-minute numbers are DESIGN JUDGEMENT, not sourced — no published cadence exists for file-based agent liveness; tune them on the first buffet run.
- **Force-push is forbidden for all agents including the coordinator** — a force-push can destroy the append-only log, which is the run's only memory.

**Branches (binding):** each agent works on its own branch `buffet/<name>` and pushes that branch. Only the coordinator merges branches into the buffet mainline (`buffet/main`); never rebase someone else's branch, never force-push. Agents never push to the mainline directly. (Access: shared-repo branches are the primary path; fork + PR is the fallback — see §9.)

### Merge-pass git procedure (RUNBOOK PROCEDURE — fills a design gap, not a designed mechanism)

The design (§§2/5) never defines how board writes reach the mainline, how the coordinator reads other agents' files, or how workers see board updates — and the runbook's own branch-protection rule (only the coordinator, on the bypass/allow-list, may push to `buffet/main` at all) forbids the obvious path. The procedure below closes that gap. It is an implementation detail of this runbook, labelled as such; it invents no design claim.

- **Coordinator → workers (board + run-log publication).** The coordinator NEVER commits directly onto `buffet/main` and NEVER pushes a non-merge commit to it. Every merge pass, the coordinator publishes board/log updates like this, from its own clone:
  ```bash
  git fetch origin buffet/main
  git checkout -b coord/board-<YYYYMMDD-HHMM>-<n> origin/buffet/main   # short-lived coordinator branch; <n> increments per pass
  # ... edit coord/BOARD.md + coord/run-log.jsonl (board writes carry coordinator-term: N, §1) ...
  git commit -m "board: pass <n> (term <N>) — <one-line summary>"
  git push -u origin coord/board-<YYYYMMDD-HHMM>-<n>
  git checkout buffet/main && git pull --ff-only
  git merge --no-ff coord/board-<YYYYMMDD-HHMM>-<n> -m "board pass <n> (term <N>)"
  git push origin buffet/main        # the ONLY push to buffet/main: the coordinator's merge commit
  git push origin --delete coord/board-<YYYYMMDD-HHMM>-<n>   # short-lived branch deleted after the merge
  ```
  The run-start human step (§9) puts the coordinator — and, on succession, the deputy acting as coordinator — on the branch-protection bypass/allow-list for `buffet/main`: those are the only actors permitted to push to it at all. "Merge commits only" is NOT a GitHub setting and is not what protection enforces: protection enforces *who* may push; the merge-only rule is a runbook convention, enforced by the agents-ignore rule in the next sentence. A board write that is not a merge commit landing through this procedure is not a board write — agents ignore it. The coordinator publishes the board + run log after EVERY merge pass this way (F18), not only after lands, so the remote is at most one pass stale. A revert of a bad board write (F23) — and a revert of a bad production merge (F6, §11) — goes through the same procedure: the revert commit lands on a fresh `coord/board-…` branch and is merged, never pushed directly. **Push-failure fallback:** if the merge-commit push is rejected (protection misconfigured), stop the pass, record the failure in the run log, and escalate to the human — never force-push, never commit directly onto `buffet/main`. **Orphan board branches:** delete the local branch too after the merge (`git branch -d coord/board-<YYYYMMDD-HHMM>-<n>`). A `coord/board-…` branch pushed but never merged (coordinator crash mid-pass) is deleted by the next pass (`git push origin --delete coord/board-<…>-<n>`) once that pass has published its own board — a board branch from a superseded term is never merged.
- **Workers → coordinator (claim reading — no landing involved).** The coordinator reads another agent's file WITHOUT merging its branch (merging would land un-gated production work). On every merge pass:
  ```bash
  git fetch origin                              # fetch all refs, including every agent branch
  git show origin/buffet/<name>:coord/<name>.md  # read the agent's file at its branch tip
  ```
  The coordinator also reads the claim's `board-hash` from that file and checks it against `git rev-parse origin/buffet/main` (stale-hash rejection, above). The coordinator never checks out another agent's branch to read a claim.
- **Workers see board updates (fetch the mainline explicitly).** `git pull --ff-only` on an agent's own branch pulls ONLY that branch — it never sees the board, which lives on `buffet/main`. Every poll, every agent runs BOTH:
  ```bash
  git pull --ff-only                            # your own branch, buffet/<name>
  git fetch origin buffet/main                  # the board lives here — this fetch is what makes the board current
  git show origin/buffet/main:coord/BOARD.md    # read the current board (or: git log --oneline origin/buffet/main -5, then show)
  ```
  The board-hash for a new claim is `git rev-parse origin/buffet/main` taken right after that fetch. An agent that only pulls its own branch is reading a board frozen at branch-creation time — awards, new slices, and takeovers are invisible to it until it fetches `buffet/main`.
- **Term fencing under this procedure.** Every coordinator board write carries `coordinator-term: N` in the board fields AND in the merge commit message (`board pass <n> (term <N>)`). Agents check the term on every fetch: a board whose term is lower than the highest term the agent has seen is superseded and ignored. A deputy taking over publishes its term-`N+1` board through the same short-lived-branch procedure (branch `coord/board-<…>-<n>`, merged by the deputy as the new coordinator); the old coordinator, on seeing a higher term, posts `STOOD-DOWN` and must not publish board writes afterwards — a board-branch merge from a superseded term is ignored by every agent, and the new coordinator reverts it through the normal procedure if it ever lands.
- **Fork + PR fallback.** If an agent works on a fork, the coordinator reads its claim from the PR head instead of `origin/buffet/<name>`: `git fetch origin pull/<n>/head && git show FETCH_HEAD:coord/<name>.md` — the fetch lands in `FETCH_HEAD`, not in a named ref, so read the file from `FETCH_HEAD`. Everything else in this procedure is unchanged — the board still publishes through the coordinator's short-lived branch + merge, and the agent still fetches `buffet/main` for the board.

### Merge protocol — who, when, verification, conflicts, bad merges

**Who merges:** the coordinator only — always, including in the fork+PR fallback (§9). The reason is a race, not a hierarchy: landing is a write to the shared mainline, and two agents landing simultaneously land on different bases, so the second land's trial-merge is instantly stale. A single merger serialises landings, so "trial-merged tree == landed tree" can actually hold.

**Landing rule:** `git merge --no-ff origin/buffet/<name>` with a merge message recording branch tip, mainline tip before the merge, trial-merge tree OID, and gate result. No squash (GitHub's own warning: long-running branches squashed then re-used make later conflicts more likely and force re-resolving the same conflicts). No `--ff-only` policy (it can only succeed for the first land after a fork). No rebase (D4). The first land of a round also uses `--no-ff`, so every land has identical shape and an identical revert path.

**Landing order:** fix the order up front (board order), record it in the run log. Land sequentially. **Before each land, trial-merge the branch against the *current mainline tip* (not the original base)** and gate on that merged tree. Pairwise trial-merges (A+B) remain useful as *early detection* on each 30-min coordinator pass, but a pairwise-clean result never authorises a land — only the trial against the current tip does. **If anything lands on the mainline between a trial and its real merge, the trial is void; re-trial.** Do not re-pick the order mid-run to dodge a conflict — reordering hides the conflict and makes the log lie about what was tried.

**Verification before landing (gate on the merged tree):**

```bash
MAINLINE_TIP=$(git rev-parse origin/buffet/main)   # <mainline-tip>: the current buffet/main tip
BASE=$(git merge-base $MAINLINE_TIP origin/buffet/<name>)
node scripts/trial-merge.mjs --base $BASE --a $MAINLINE_TIP --b origin/buffet/<name> --worktree /tmp/trial-<name>
```

`scripts/trial-merge.mjs` runs `git merge-tree --write-tree` (exit 0 = clean, 1 = conflicts) and, with `--worktree`, checks the merged tree out into a detached worktree for gating. The gate runs ON the merged tree — `impeccable detect` + Playwright screenshots at 1440/768/390 — and the worktree is removed after the land decision for that slice (gate + cross-check + grade), not right after the gate: the pre-land cross-check (§14) runs on the merged tree in the trial worktree, so removing it after the gate would leave the cross-check with no tree. Record the merged tree OID + gate result + cross-check verdict in `coord/run-log.jsonl` *before* the real merge. **The land requires gate green AND cross-check clear (no SEVERE; warnings fixed-or-waived, §14).** **Per-branch green is not green:** a branch can pass its own gate and still break the merged page (two agents editing `tokens.css` compatibly at the text level but contradicting each other semantically; two variants both valid alone). The merged-tree gate is the only gate that counts.

**Early conflict detection:** on every 30-min coordinator pass, run `merge-tree --write-tree` for every pending branch against the current tip (and every pending pair) and log clean/conflict per pair. The pair trial's base is the merge-base of the two branches (`BASE=$(git merge-base origin/buffet/<a> origin/buffet/<b>)`). A pairwise result is **early warning only**: it never authorises a land, and a pairwise conflict does **not** consume a merger attempt — the merger starts only on a conflict against the current tip, so a phantom conflict (clean against the tip) never wastes the capped 1-attempt merger. At ~0.02 s per replay in published logs, there is no reason to discover a conflict only at landing time; early detection lets the neutral merger start while the agents are still working. (If pairs are ever batched with `git merge-tree --stdin`, parse the embedded per-merge status — the process exit code is 0 for both clean and conflicted merges in that mode.)

**Conflicts:**
- **Text conflict → neutral merger** (fresh-context agent, NOT the coordinator — D4). The merger receives both branch tips + the merge base + the conflicted-file list + each branch's slice intent (from the board), works in its own throwaway branch (`merge/<a>-<b>-<n>`, where `<n>` is a counter the coordinator increments per pair and records in the run log), never touches `buffet/<a>` or `buffet/<b>`, never force-pushes, and produces a *resolution* that is itself trial-merged and gated on its merged tree before landing. Cap: **1 attempt**, enforced by `scripts/trial-merge.mjs` via an attempts ledger — the coordinator passes `--attempt-log coord/merge-attempts.jsonl --attempt-key <a>+<b>@<base>` when trial-merging a merger resolution; the script exits 2 if the key already exists in the log (same pair-state = same a+b+base; a branch change = new pair-state = fresh attempt). Early-detection trials without the flags never consume an attempt. On failure: both branches stay unlanded, board marks the slice `input-required`, run log records the attempt + the conflict list, decision waits for human-on-return. The coordinator never "just fixes it quickly" — that reintroduces the self-dealing the neutral role exists to prevent. **Merger failure kinds:** a tool/transport failure (no resolution produced) does **not** consume the attempt; only a produced-but-gated-red resolution consumes it. The second merger source is the coordinator's own fresh subagent, or a `NEED-MERGER` claim by another agent (§1).
- **New pair-state rule:** if a branch changed since the failed attempt (agent pushed a fix), that is a new pair-state, not a second attempt — re-trial-merge first, then a fresh single merger attempt if it still conflicts.
- **Gate-red but text-clean (semantic conflict) → back to the owning agent(s) with the gate output**, not to the merger (there is no text to merge). Publication: the coordinator sets the row to `input-required`; the Notes column carries the gate-output summary + a link to the gate record in the run log; the owning agent re-claims with a new plan on its next pull (the slice returns to `working` on re-claim). This is the more dangerous case and has no text conflict to point at.
- **Why conflicts are expected, not exceptional:** plan on ~2-in-5 textual conflict per cross-agent pair (Xu et al. 41.7%, sample-conditioned — see scale note below), and remember 47.3% of textual conflicts occur with *disjoint* authored file sets, so ownership does not prevent them. The mitigations are the ones in this section, not the ownership table.

**Scale note:** only **0.5%** of co-active pairs are cross-agent — **41.7%** is the conflict rate *given* a cross-agent pair, which is rare (Xu et al., arXiv:2607.04697). Treat the 41.7% as a warning about cross-agent pairs, not as the expected conflict rate for this run. The 41.7% is **sample-conditioned** (stratified 115/716 evaluable replays; matched same-repo analysis weakens it to 28.3% vs 43.3%, p=0.078); the authors explicitly refuse a cross-vendor-penalty claim. Quote it with the qualifier or not at all. (The Xu et al. full PDF — methods/CI bounds — is CHƯA ĐỌC; the abstract + §3.1/Table 1 of the follow-up were read.)

**Bad-merge recovery, by case:**

| Case | Recovery |
|---|---|
| Gate fails on the merged tree, before landing | Nothing landed; discard the trial worktree; branches untouched; pair goes to the neutral merger (text-conflicted) or back to the owning agent(s) with the gate output (gate-red). |
| Merge landed locally, not yet pushed | `git reset --hard ORIG_HEAD` to the pre-merge tip (VERIFIED 2026-11-11, git-scm.com/docs/git-reset — merge/pull always leave the pre-merge tip in `ORIG_HEAD`, so resetting hard to it restores the index, working tree, and branch tip). Push promptly after verified lands so this window stays short. |
| Merge landed and pushed, then found bad | `git revert -m 1 <merge-sha>` (VERIFIED) on a short-lived branch, landed into `buffet/main` with `git merge --no-ff` through the §5 merge-pass procedure — the revert commit itself is never pushed directly; record it in the run log. **Trap:** after the revert, re-landing the *same* branch brings in nothing — the fix must come as **new commits on a rebuilt branch** (or a revert-of-the-revert followed by the fixed merge). **Who rebuilds:** the OWNING agent rebuilds its branch with new commits (D4 — the coordinator never touches the agent's branch). The coordinator publishes the revert + the rebuild request on the board (row → `input-required`, Notes: "merge reverted <sha>; rebuild with new commits, then re-claim"); the owning agent learns it on its next pull. An agent that simply re-pushes its old branch tip after a revert will watch its merge "succeed" while its work stays missing. |
| Merge in progress, conflicted, coordinator stuck | `git merge --abort` (VERIFIED) reconstructs the pre-merge state — provided the tree was clean when the merge started. **Coordinator hygiene:** the coordinator merges only from a clean tree (land merges on its main checkout or a dedicated clean worktree, with nothing uncommitted). |
| Lost work | **Invariant:** no agent branch is ever deleted or force-pushed by anyone but its owner, and never until the run is closed. A branch landed-then-reverted still exists on the remote with all its commits; a branch that failed the gate still exists; a merger's throwaway branch is deleted only after its resolution lands or is formally abandoned in the log. |

**Script notes:** `scripts/trial-merge.mjs` is correct in its exit-code handling and its detached-worktree workaround. Two robustness fixes applied in the v2 build (gen-10, verified with real merges): the tree-OID validation accepts 40-hex (SHA-1) or 64-hex (SHA-256) OIDs; conflict lines are the conflicted-file-info section only — the informational-messages section (separated by a blank line) is excluded from the conflict count.

**Milestone posts to the Optimus group:** the coordinator posts a short status line ONLY when a milestone lands (loop stopped, Figma export done, human return complete, run invalid + redo started). One line, e.g. "xong vòng build, Figma đã xuất — đang chờ người về sửa". No coordination detail, no error dumps, no agent-to-agent messages. Mie never posts there.

## 7. Human return (what the humans do when they come back)

**Option R1 — edit in Figma, agents regenerate code.** The human edits variables/components/frames in Figma (Page 02 is built for this), then says one line: "Figma changed, regenerate". The agents: (1) re-pull Figma (A first — human re-exports the changed variable modes; B/C only if already set up); re-pull is human-triggered or version-triggered (Figma `version` changed since SOURCE.md), never on a timer. (2) Re-lock `tokens.css` (new lock entry; old lock kept in history). (3) Rebuild → re-gate → re-grade against the NEW Figma values. (4) Re-export to Figma. **What regenerates:** `tokens.css`, the HTML, ground-truth files, the score table. **What does NOT happen:** the running app does not auto-update — re-serve/rebuild the page and refresh the browser. Copy edits in Figma flow back only if the copy is in a text layer the agent re-reads; Figma components do not become code components automatically.

**Option R2 — edit directly on the built product.** The human edits `tokens.css` and/or the HTML directly (or describes the change in words). The change enters at step 5 (token diff) or step 1 (re-lock), then gate → grade → stop. This needs no Figma at all and is the fallback whenever Figma write-back is unavailable. **Never both on the same round without a re-lock:** if the human edited BOTH Figma and the CSS, the Figma re-lock wins for token values and the direct CSS edit is re-applied after, logged as a conflict in the run log.

## 9. Clone-and-go + acceptance test

**§9 access — DECIDED (2026-11-11 12:23, by Muse per the user's delegation "ông thấy sao tốt nhất thì ông chọn"):** **shared-repo branches = PRIMARY path; fork + PR = FALLBACK.** The design (§10) reserved this decision to the user; the user delegated it to Muse at 12:23 on 2026-11-11, and the decision taken was shared-repo branches primary, fork+PR fallback. Recorded here and in `coord/BOARD.md` §9 so it is no longer unrecorded. All four humans are granted write access to the one repo and work on shared branches `buffet/<name>`. Reasons, from GitHub's own docs (VERIFIED):
1. **Fork PR workflows may require manual maintainer approval before CI runs** ("Workflow runs triggered by a contributor's pull request from a fork may require manual approval from a maintainer with write access"). On hackathon day, with humans away from machines, an approval gate nobody is present to click is a stall. Branches run CI normally. (Premise note: the repo's CI workflows are not named or verified in any file read for this design — the acceptance test names them; if no CI workflows exist, this reason is moot and branches still win on reason 2.)
2. **Coordinator-only merge is enforceable on branches** (branch protection restricts merging to the coordinator; CODEOWNERS adds required review — it is a review mechanism, not a merge-exclusivity mechanism). On forks the merge still sits with whoever has upstream write access, and "Allow edits from maintainers" is the only path for the coordinator to push fixes into an agent's PR branch — unavailable for organization-owned forks.
3. **Forks do not change who can merge and do not fix conflicts** — the conflict evidence is orthogonal to branches-vs-forks; conflicts happen at merge time either way, and 47.3% happen with disjoint file sets either way. A fork is also not a privacy boundary inside the network (commits pushed to any repo in a network can be accessible from other repos in it, including upstream).
4. The cost of branches is exactly one human decision: the push-access grant. The cost of forks is a recurring approval gate on the day the humans are absent.

**Run-start human step (both outcomes):** before the run, a human enables **branch protection on the mainline** (`buffet/main`) and puts the coordinator — and, on succession, the deputy acting as coordinator — on the bypass/allow-list: the only actors permitted to push to `buffet/main`. "Merge commits only" is a runbook convention (agents ignore any board write that is not a merge commit landing through the §5 procedure), not a protection setting — GitHub protection cannot distinguish a merge commit from any other commit. If a merge-commit push is rejected, the coordinator stops the pass, records the failure in the run log, and escalates to the human; it never force-pushes and never commits directly onto `buffet/main`. This is the enforcement behind the force-push ban and the wrong-branch-push recovery (F23) — the coordinator cannot enforce a push-side block on its own; the protection is a server-side rule set by a human once.

**Fork + PR fallback (only if push access is denied):** each agent works in its own fork and opens a PR; the coordinator remains the only merger and merges the PRs (GitHub's `--no-ff` merge-commit button is the equivalent of §5's landing rule); the trial-merge still runs locally first. Two fork-specific rules:
- **CI-approval check (procedure, not a slogan):** on every merge pass the coordinator runs `gh pr checks <n>` and `gh run list` for each open PR. If `gh` is unavailable on the coordinator's machine, the check is skipped and recorded as skipped in the run log. A PR stuck in "awaiting approval" with humans away is a **stall, not a queue**: the slice stays `working`, the coordinator records the stall in the run log, the other slices continue, and the stalled slice is carried to the human-return packet. There is no recovery that unblocks a PR without a human clicking approve — this runbook does not pretend otherwise.
- **Fork-aware claim arbiter (solved — the same rule as §5):** the arbiter is the coordinator's first-seen order in both outcomes. In the fork case the observation is the PR: if two claims for the same slice are first observed in the same merge pass, the tie-break is the **earlier PR creation time**; if no PR exists yet for either claim, the tie-break is the lexicographically smaller claim-commit hash (§5). Nothing about the arbiter is delegated to the build worker.

**Clone-and-go:** a fresh agent clones the repo, follows the README paste-prompt + `./install.sh`, runs `./verify.sh`, opens this runbook, and is working. No missing pieces, no tribal knowledge. Verified with a scratch-HOME run if possible; at minimum every file referenced by this runbook and the README must exist (the build worker checks this by listing them before inviting the other agents).

**Acceptance test for this milestone:** the other three agents — **Mie, Migga, Milo** — clone the repo and start working with no other setup. PASS = all three, cold, can (i) clone, (ii) run `./install.sh` + `./verify.sh` (or report the exact failure), (iii) open this runbook and find their role + their file + the merge protocol without asking a human, (iv) complete one assigned slice (one builder round / one expert review / one judge grade — **builder and judge slices assigned to different agents; the same agent must not grade a slice it built**) with the run log updated, (v) post a TOOLS inventory block in their own file verified by running the command (not assumed), (vi) answer a CENSUS REQUEST with a live sub-agent count in the §4 format. FAIL = any one of the three needs a human to explain a step, finds a referenced file missing, or cannot tell what to do next from the repo alone. **Precondition:** the §9 blank is filled — it is filled above (shared-repo branches primary, fork+PR fallback). **Checks:** the coordinator's machine must have modern git — `git --version` ≥ 2.38 (`merge-tree --write-tree` needs ≥ 2.38; `worktree add --detach` does not — it predates 2.38 by years) — + the gate tooling (impeccable + Playwright) — asserted in the test, not assumed; **gate tooling is asserted on ALL FOUR machines** (the deputy's machine included — a deputy that cannot run the gate cannot land anything, F29); **the repo's CI workflows are named by the test** — if no CI workflows exist, the §9 fork-approval reason is moot (branches still win on enforceable coordinator-only merge).

## 13. Context engineering — the memory architecture

**Source:** a ~30-min talk by an Anthropic engineer on context engineering (Facebook video, posted 2026-11-08; concepts as provided in the user's share, access date 2026-11-11) + Anthropic's "Effective context engineering for AI agents" post (read lines 0–153 of 226, 2026-11-11 — context as the set of tokens at inference time; context rot / attention budget; progressive disclosure and just-in-time retrieval via filesystem navigation; compaction, structured note-taking, multi-agent architectures for long-horizon tasks). **Honesty note:** the post's caption claims "90% of Anthropic engineers build self-prompting systems" — that is the poster's hook, not something the transcript establishes. It is not cited as fact anywhere in this runbook.

**The journey — and the validation of the kit's architecture:** AGENTS.md files (dead simple, human-readable, injected at session start — surprisingly effective; the problem is context bloat as they grow) → memory tools (agents self-manage read/write/update within a session) → Skills with progressive disclosure (read a few lines, load the body only when needed — deep detail without overloading context; the bookshelf analogy) → memory-as-a-filesystem (let agents use plain filesystem search/read/write instead of bespoke memory tools; search mirrors progressive disclosure; index the memory well). **The kit already uses AGENTS.md + skills + progressive disclosure — the talk validates that architecture; this runbook builds on it rather than replacing it.** The runbook is the AGENTS.md pattern (human-readable, injected at run start); the `frontend-kit` skill is the progressive-disclosure pattern (a short skill file, deep detail loaded only when needed); the repo is the memory filesystem (the board, the run log, the task files, the taste lock — all plain files, searchable with grep/glob, no bespoke store).

**Production guardrails — required primitives, not optional ideas:**

1. **VERSIONING** — track versions, restore old ones, record which session/conversation led to each update and who did it. In buffet mode: the board carries `coordinator-term` (the version of the coordinator); the run log records every board/state change with the merge pass that made it, the actor, and the reason; TASTE.md / tokens.css / skill changes go through the coordinator with a version stamp in the run log. Nothing is overwritten silently — append + supersede (the F14 rule).
2. **CONCURRENCY via hash-based optimistic locking** — read hash, edit, re-hash before write; mismatch = reload and retry. In buffet mode: **the lock is the git push** (atomic per-ref). The coordinator reads the board at a commit hash, writes, and pushes; if the push fails because the remote moved, the coordinator reloads and retries. Claims carry the board hash they were read against; the coordinator rejects a claim whose board-hash is stale. This is the mechanism behind the §5 arbiter — the coordinator's first-seen order works because the push is the atomic compare-and-swap.
3. **TIERED ACCESS** — org-wide curated knowledge → team layers → personal scratchpads; agents mostly read org context and write only their own scratchpad. In buffet mode the tiers are the file rules: **org tier** = TASTE.md + AGENTS.md + the skill (read by all, written only by the coordinator/human); **team tier** = BOARD.md + `coord/tasks/<id>.md` (coordinator writes, agents read); **personal tier** = each agent's own `coord/<name>.md` (the agent writes, others never touch). The one-writer-per-file rule is the tiered-access rule, restated.
4. **PORTABILITY** — memory is valuable org/user/task-specific context; design it clean and portable across agents/platforms. In buffet mode the memory *is* plain files in the repo — no bespoke store, no platform lock-in; any agent that can clone the repo can read the whole memory. This is also why the git file blackboard beat Issues/A2A/MCP: the work product and the coordination state live in the same portable place.

**DREAM — out-of-session memory refinement (a designed step, not an afterthought):** after builds (and after the hackathon run), a dedicated Dream pass runs: a fresh-context agent with dedicated resources, offline/async, reviews the build transcripts + the run log + the taste/skill files, finds cross-session patterns (e.g. every agent failing the same way, a tool call repeatedly failing, a missing topic), and proposes memory updates **with evidence + stats**. A human accepts or rejects each proposal. Proposals are published as `DREAM-PROPOSAL` rows on the board; **nothing is applied without human approval**. Analogy from the talk: school — students (agents), teachers (graders/judges), principal (the Dream pass — sees everything, adjusts the curriculum). Contrast with in-session memory, which is limited: resources are split between the task and curation, and it has no cross-session pattern visibility. The Dream pass is a step in the run sequence (§4: after the human-return packet, before the next run). **Expected results (the talk's reported results, as direction not promise):** better accuracy on repeat tasks (memory records past mistakes), lower latency/cost (agents finish first try), agents start writing their own memory, developers freed to focus on product success. For buffet mode these are measured by §9 instrumentation across runs — the Dream step is what turns one run's log into the next run's improvement.

## 14. Cross-checking team — security, safety, compliance (MANDATORY, same level as the deterministic gate)

**Standing requirement (2026-11-11 — EXTREMELY important):** the workflow includes a DEDICATED CROSS-CHECKING TEAM for security, safety, and compliance. It is independent from the builder and from the design judge, with BLOCKING authority on severe findings (the same model as the existing GUARD: SEVERE = hard stop). It is a mandatory stage, on the same level as the deterministic gate — not an optional review, not a post-ship audit.

**Who runs it:** independent agents, never the builder of the slice, never the design judge for that slice, and never an agent with production history of the slice. The coordinator summons the cross-checkers as its own subagents on its own machine (the §1 line: the coordinator commands only its own subagent instances). Per pre-land check, one fresh-context cross-checker runs the full checklist; per pre-ship check, the team runs as two agents (one for security/data-leaks, one for ToS/copyright) and consolidates into one report. (Team size is DESIGN JUDGEMENT.)

**Where it runs in the loop (before merge/ship, not after):** twice. (i) **Pre-land, per slice:** after the deterministic gate, before the judge grade — on the merged tree in the trial worktree (§5). The land requires gate green AND cross-check clear. (ii) **Pre-ship, once:** on the shipping version (the mainline tip at stop), before the human-gate packet is prepared. A SEVERE finding at either point stops the land/ship exactly as a gate FAIL does.

**What it checks (minimum — the team defines its full checklist):**
- (a) **Web/app SECURITY:** XSS, injection (SQL/command/template), secrets/keys/tokens left in code, insecure dependencies (known-vulnerable versions), auth/session flaws (broken auth, session fixation, missing CSRF where state changes, insecure cookies).
- (b) **DATA LEAKS:** PII, credentials, or private data leaking into output, code, logs, screenshots, or shipped files (including the Figma export and the human-gate packet).
- (c) **TERMS OF SERVICE compliance:** third-party services, APIs, scraping, and embedded content used within their terms (rate limits, attribution requirements, no scraping where forbidden, API keys used only for their permitted purpose).
- (d) **COPYRIGHT:** images, fonts, code, copied content, and prompts must not ship copyrighted material without a licence. The kit's existing precedent — "cite only, never copy the PDF" — is generalized: the default is citation (link + attribution); copying is the exception and requires a licence. Stock assets, fonts, and code snippets are checked against their licences; AI-generated content is checked against the model's terms.
- (e) **"Và nhiều nữa" (and much more):** the team itself defines its full checklist beyond (a)–(d) — the seed above is the floor, not the ceiling. The checklist lives in the repo at `coord/CROSSCHECK.md` (coordinator-owned; the team proposes changes, the coordinator records them) and is **verified by an independent red team before it becomes binding** (the red team checks the checklist for completeness and correctness, not just the findings).

**What blocks vs warns:**
- **SEVERE = hard block.** No landing, no ship. The slice goes to `input-required` with the report linked; the owning agent fixes and re-claims; the fix is re-checked by a fresh cross-check run. The coordinator can NEVER waive a SEVERE — only the human, on return, can override one, and the override is recorded in the run log with the human's name.
- **WARNING = fix or waive-with-reason.** The warning must be fixed, or the coordinator waives it with a written reason in the run log (accepted risk, named, dated). A waived warning is still visible in the pre-ship report.
- **OK = clear.** Recorded in the run log; the land/ship proceeds.

**How it reports:** each check produces a report at `coord/crosscheck/<slice-id>-<n>.md` (coordinator-owned directory; the cross-check agent writes there as the coordinator's subagent). Findings carry severity + evidence (file:line, what, why, suggested fix). The coordinator transcribes the verdict (SEVERE count, WARNING count, OK) into the run log before landing. The pre-ship report is attached to the human-gate packet and is filed as `coord/crosscheck/ship-<n>.md` (the shipping version has no slice id).

**Failure modes:** F31–F33 (§11).
